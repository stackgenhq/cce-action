Quick start

One small workflow.
A useful first report.

Create .github/workflows/cce.yml in your repository. The workflow checks out your code, runs CCE, and uploads the results.

  1. 1Add the workflow and commit it.
  2. 2Open the CCE run in GitHub Actions.
  3. 3Download the cce-results artifact.
Open the complete example ↗
.github/workflows/cce.ymlYAML
name: CCE
on: [push, pull_request]

permissions:
  contents: read
  packages: read

jobs:
  scan:
    uses: stackgenhq/cce-action/.github/workflows/scan.yml@v1
    with:
      language: AUTO
      filter: cloud
Prefer a fixed version? Use @v0.3.0 instead of @v1. The major tag receives compatible updates; an exact release stays fixed.

WHAT

Normalized API evidence

The row identifies AWS, Secrets Manager, and get_secret_value. The ten summary rows are evidence records, not ten unique permissions.

WHERE

A source location you can inspect

File, line, column, method, and signature connect the classification to the code. The full guide links directly to the pinned source line.

WHY

A better review starting point

An IAM reviewer can evaluate secretsmanager:GetSecretValue, then choose the secret ARN and validate the role. CCE does not grant access automatically.

Evidence, not a runtime guarantee.

The scan does not execute code, read secrets, prove runtime coverage, or test effective IAM. Use it alongside human review and runtime validation.

Make CCE speak your language

Your code has its own vocabulary. A lens teaches CCE to recognize it.

A lens is a small YAML file that describes the libraries or patterns you want to find. Use one to inventory internal SDKs, legacy clients, or technology-debt patterns alongside built-in cloud mappings.

  • Keep lens definitions with your code.
  • Pin remote content so changes are visible.
  • Test changes against fixtures before rollout.

Designed for responsible review

Useful evidence. Clear boundaries.

CCE supports engineering decisions; it does not replace testing, provider documentation, or an IAM reviewer.

Private by default

No CCE account is needed. Field diagnostics are off unless you explicitly enable them. Basic scans use read-only repository permissions.

Traceable results

Reports connect operations to source locations. Lens hashes and versioned artifacts help reviewers understand what produced a result.

No guessed permissions

Strict GCP and Azure exports do not publish unverified permission mappings. A missing role export is not silently replaced with a guess.

Static-analysis limits

Dynamic, reflected, or unrecognized wrapped calls may be missed. An empty result does not prove that a service needs no permissions.

IAM requests are review input, not ready-to-deploy policy.

CCE identifies operations in source code. Your reviewers remain responsible for resource scope, runtime behavior, organizational policy, and final approval.

Good to know

Practical details

Runner
Linux with Docker; ubuntu-latest is the simplest choice.
Languages
Go, Python, Java, and JavaScript. Use AUTO for detection.
Results
JSON reports, workflow artifacts, optional HTML and SARIF, and selected IAM exports.
Custom providers
Use filter: all when a lens reports categories outside the cloud filter.
Large repositories
Scan a subdirectory or set scan-timeout to keep CI bounded.
Fork pull requests
Review artifacts remain available; comments and SARIF publication are skipped when the token cannot write safely.

Common questions

Do I need to install CCE separately?

No. The reusable workflows and composite actions provide a tested CCE version for the run.

Can I use CCE inside an existing job?

Yes. Check out your repository, then use stackgenhq/cce-action@v1 or a focused subaction such as access-request@v1.

Where do my reports go?

They are written to the configured output directory and, in the reusable workflows, uploaded as GitHub Actions artifacts.

Is this a compliance or least-privilege verdict?

No. It is source-code evidence for review. Validate policies against runtime needs and your organization’s requirements.
